FitOS Equipment SDK 整合指南 FitOS Equipment SDK Integration Guide

讓你的 Android App 透過 FitOS 主機讀取健身設備的即時運動數據,並控制速度、坡度、阻力與訓練啟停。本文件涵蓋 API v1 的全部公開介面。 Read live workout telemetry from fitness equipment through the FitOS host, and control speed, incline, resistance and workout start/stop — from your own Android app. This document covers the complete public surface of API v1.

概覽Overview

FitOS 是健身機台上的主控 App。你的 App 透過一個 AIDL bound service 與 FitOS 溝通,即可讀取設備的即時運動數據、查詢設備狀態,並送出控制指令。

FitOS is the console app on the equipment. Your app talks to it through an AIDL bound service — that is how you read live workout telemetry, query equipment state and send control commands.

你可以做什麼What you can do

讀即時運動數據Live telemetry

速度、心率、距離、卡路里、功率、阻力、坡度、迴轉數、步頻、划船與爬梯數據等 37 個欄位,每秒推送一次。

37 fields — speed, heart rate, distance, calories, power, resistance, incline, cadence, stride rate, rowing and stepping metrics — pushed roughly once per second.

控制設備Control the machine

設定速度、坡度、阻力、爬梯段速,以及啟動 / 停止機台訓練。

Set speed, incline, resistance and stairmill speed level; start and stop the workout on the machine.

讀設備狀態Read equipment state

連線狀態、設備型別、裝置名稱、型號、硬體與韌體版本、控制狀態與單位制。

Connection status, equipment type, device name, model, hardware and firmware version, control state and unit system.

讀控制範圍Read control ranges

每種設備的阻力 / 坡度 / 速度 / 段速上下限,用來畫 UI 滑桿或做輸入驗證。

Per-equipment minimum and maximum for resistance, incline, speed and level — for building sliders or validating input.

支援的設備型別Supported equipment types

飛輪(Bike)、划船機(Row)、跑步機(Run,含一般跑步機與弧形跑步機)、爬梯機(Stairmill)。

Bike (Bike), rower (Row), treadmill (Run, covering both standard and curved treadmills), and stairmill (Stairmill).

連線通道對你是透明的Connection channels are transparent to you

設備可能透過 BLE、USB 或 UART 與機台連接。FitOS 負責處理所有通道差異;你拿到的 API 與資料格式在三種通道下完全一致,不需要為此寫任何分支邏輯。

Equipment may be attached over BLE, USB or UART. FitOS absorbs every difference between them — the API and the data you receive are identical in all three cases, so you never need to branch on the channel.

設備連線由 FitOS 管理FitOS manages the equipment connection

設備的配對與連線由 FitOS 處理。你的 App 透過 onConnectionStateChanged 觀察目前的連線狀態與設備型別,並據此調整 UI — 例如尚未連線時停用控制項。

Pairing and connecting to the equipment is handled by FitOS. Your app observes the current connection status and equipment type through onConnectionStateChanged and adapts its UI accordingly — for example, disabling controls while nothing is connected.

Calling setIncline() on a bike produces no error and no effect — matching the behaviour of the FitOS console itself. Read EquipmentState.equipmentType to decide which controls to show, rather than relying on exceptions to detect support.

超出範圍的數值會被箝制,不會被拒絕Out-of-range values are clamped, not rejected

送出超過設備上下限的值時,主機會箝制到最接近的合法值後才下達給機台 — 不會拋例外,也不會忽略整個指令。你會在後續的遙測中看到被箝制後的實際值。建議送出前就先用 getLimits() 的範圍夾好,讓你的 UI 顯示與實際值一致。

A value beyond the equipment's range is clamped to the nearest legal value before it reaches the machine — nothing is thrown and the command is not dropped. Subsequent telemetry will report the clamped value. Clamp against getLimits() before sending, so your UI and the machine agree.

重要注意事項Important notes

這一節的四點是整合時最容易出錯的地方,請務必讀完。

The four points in this section are where integrations most often go wrong. Please read all of them.

1. 單位語意 — 送出值與範圍值的單位不同1. Unit semantics — the value you send and the range you read use different units

這是 v1 最容易踩的坑This is the easiest mistake to make in v1
  • setSpeed(double) 的單位跟隨主機單位設定:EquipmentState.isMetric 為 true 時是 km/h,false 時是 mph。
  • EquipmentLimits.runSpeedMinKmh / runSpeedMaxKmh 一律是 km/h,與單位設定無關。
  • EquipmentSnapshot.speed 等顯示字串已依主機單位換算,與 setSpeed 同單位。

因此在英制模式下,不能直接拿 runSpeedMaxKmh 去夾 setSpeed 的參數 — 必須先換算。

  • setSpeed(double) takes its unit from the console setting: km/h when EquipmentState.isMetric is true, mph when it is false.
  • EquipmentLimits.runSpeedMinKmh / runSpeedMaxKmh are always km/h, independent of that setting.
  • EquipmentSnapshot.speed and friends are already converted to the console unit — same unit as setSpeed.

So in imperial mode you cannot clamp a setSpeed argument directly against runSpeedMaxKmh — convert first.

2. 使用 startWorkout() / stopWorkout() 的注意事項2. Using startWorkout() / stopWorkout()

使用這兩個方法前請先了解Before you use these two

這兩個指令的作用對象是機台本身。使用時請留意:

  • 運動資料的保存請視為你的 App 的責任。不要假設主機端會為你記錄或上傳這段訓練。
  • 指令不保證一定生效。當主機端本身已有進行中的訓練流程時,為避免雙方對「訓練是否進行中」認知不一致,主機可能不會執行你送出的啟停指令。
  • 請以 onControlStateChanged 回報的狀態作為判斷依據,不要在送出指令後就假設狀態已改變。

適用情境:你的 App 位於前景、且是這次訓練的主要控制者。啟動前先檢查 controlState,若已是 CONTROL_STATE_START 代表訓練已在進行中,不需再送啟動指令。

These two commands act on the machine itself. Keep in mind:

  • Treat persisting the session data as your app's responsibility. Do not assume the host will record or upload the workout for you.
  • A command is not guaranteed to take effect. When the host already has a workout flow of its own in progress, it may decline to act on your start/stop command, so that the two sides do not end up disagreeing about whether a workout is running.
  • Use the state reported by onControlStateChanged as your source of truth — never assume the state changed just because you sent a command.

Intended usage: your app is in the foreground and is the primary controller of this session. Before starting, check controlState — if it is already CONTROL_STATE_START a workout is in progress, so there is no need to start again.

3. 指令是非同步且不回報結果3. Commands are asynchronous and report no result

所有控制方法呼叫後立即返回,不代表機台已經執行。實際結果請一律透過回呼觀察:onControlStateChanged 確認訓練啟停,onEquipmentDataChanged 確認速度 / 坡度 / 阻力已生效。不要在送出指令後立刻假設狀態已改變。

Every control method returns immediately; that return says nothing about whether the machine acted. Always confirm through callbacks: onControlStateChanged for start/stop, and onEquipmentDataChanged for speed, incline and resistance taking effect. Never assume the state changed just because the call returned.

4. 設備狀態可能由你以外的來源改變4. Equipment state can change from outside your app

你的 App 不是唯一能影響機台的角色 — 使用者可以直接在機台面板上操作,主機端本身也可能送出控制指令。因此你設定的數值有可能在稍後的遙測中變成別的值,後送出的指令會蓋掉先前的。請一律以回呼回報的值來更新 UI,不要把「我剛送出的值」當作顯示來源。

Your app is not the only thing that can affect the machine — the user can operate the console directly, and the host may issue control commands of its own. A value you set may therefore show up as something else in later telemetry, since a later command overrides an earlier one. Always drive your UI from the values reported in callbacks, not from the last value you sent.

生命週期與重連Lifecycle & reconnect

建議的綁定時機When to bind

在 onStart() 呼叫 connect()、onStop() 呼叫 disconnect()。這樣 App 進入背景時不會佔用主機資源,回到前景時 registerCallback 的補推機制會立刻把你帶回最新狀態。

Call connect() in onStart() and disconnect() in onStop(). Your app then holds no host resources while backgrounded, and on return the replay behaviour of registerCallback brings you straight back to current state.

版本相容性Versioning

這份契約以向後相容為設計目標:新功能會以追加的方式加入介面尾端,既有方法的簽章與順序會盡量維持穩定,讓既有整合在主機更新後能持續運作。

This contract is designed for backward compatibility: new capabilities are added by appending to the end of the interface, and the signatures and order of existing methods are kept as stable as we can, so an existing integration keeps working across host updates.

請務必用 getApiVersion() 做功能偵測,不要假設主機一定支援你編譯時的所有功能 — 機台在現場的軟體版本不一定與你手上的 SDK 同步。

Always feature-detect with getApiVersion() rather than assuming the host supports everything you compiled against — the software version on a unit in the field will not necessarily match the SDK you are holding.
